# 统一实施路线图

状态：待用户审阅的提案。2026-11-03。除了本轮审计文档和隔离原型，以下开发尚未授权。已有改动提交授权不等于 Phase 2 开发授权。

## 顺序与验收关口

| 阶段 | 工作 / 产物 | 进入下一阶段的条件 | 建议投入（单人有效工作日） |
|---|---|---|---|
| Phase 0 本地审计 | 真实安装、源代码、文档、隔离行为测试；记录不能核实的运行状态 | 基线可识别，风险与缺口显式列出 | 本轮已执行可访问范围 |
| Phase 1 架构与体验设计 | 数据映射、协议提案、导航、设计系统、交互原型、恢复标准 | 用户批准；找到并验证实际 ZCashflow 安装/Android 版本；特殊类型有可行映射 | 本轮已形成提案，待评审 |
| Phase 2 桥接可行性验证 | 在独立虚构库打通 Z 原生写入路径、loopback认证、交易CRUD、账户分类预算、Android重连、删除传播与恢复 | 并发/崩溃/删除/重复请求/未授权访问全通过；不满足则返回设计 | 6–12 |
| Phase 3 Fox 数据层 | repository 适配器；保留 dataLayer 工作台门面；统一 ID、金额/日期、版本与错误 | CRUD 与聚合语义回归，离线明确只读且不假成功 | 4–8 |
| Phase 4 UX/UI 分批替换 | 快速记账→交易→账户/分类→预算→森林→分析/年轮→设置 | 每批先评审后替换；键盘/窄窗/状态/统计用例通过 | 8–15 |
| Phase 5 迁移与镜像 | 先在备份副本 dry-run，对账、隔离不支持记录；镜像差异审核；原账本不覆盖 | 恢复演练通过，用户逐批确认异常；正式迁移另行授权 | 5–10 |
| Phase 6 切换 | 冻结旧写入、最终增量、校验、双设备验证、用户签收 | 新数据回退有增量账本；旧系统仅归档；避免双写 | 3–6 |

估算合计 26–51 个有效工作日，前提是单人熟悉 TS/Rust、已有设备与环境可用；不含等待评审、上游修复、未知同步缺陷与投资模型扩展。不是工期承诺。

调整建议：把“迁移映射设计、镜像冲突设计、恢复标准”提前到 Phase 1；在 Phase 2 就验证手机删除传播和恢复，避免界面完成后才发现数据源不适配。真实迁移仍留到 Phase 5。不要为统一外观重写已能复用的 Obsidian 宿主、Canvas 图表或工作台事件。

## 预计修改范围（未来，非本轮改动）

Fox 原文件：`finance.ts`（从文件存储转为兼容门面）、`main.ts`（连接生命周期/设置/事件）、`finance-modal.ts`、`finance-tx-modal.ts`、`finance-adjust-modal.ts`、`finance-cash-modal.ts`、`finance-view.ts`、`finance-review-view.ts`、`styles.css`。新模块建议 `finance-client.ts`、`finance-mirror.ts`、`finance-reconcile.ts`，仅在职责确需拆分时建立。版本文件、构建产物在正式开发交付时一致更新。

Z 的实际文件以 integration-architecture.md 固定提交地图为准：`src-tauri/src/lib.rs` 与共享 Db/commands/services/sync 路径；新增本机桥接模块。不能只新增 HTTP handler 绕过现有同步与加密持久化。

工作台调用方：`.obsidian/plugins/fox-dashboard/view.ts:1233` 通过 `ff.dataLayer` 调用。优先维持门面和 `fox-finance:updated`，仅在不能兼容时申请工作台变更，不连带改造收藏室等无关模块。

Vault 中的旧 Finance 目录、本地插件 `data.json` 与数据库均为迁移输入或敏感配置，不能提交 GitHub。新镜像目录需用户确认并与旧账本分离。

## 停止条件

无法无损表示特殊交易、同步会复活已删除记录、对账差异非零且原因未知、恢复失败、鉴权绕过、明文镜像范围未确认，任一出现都不得正式切换。保留当前版本继续使用，不通过补写平衡记录掩盖异常。
